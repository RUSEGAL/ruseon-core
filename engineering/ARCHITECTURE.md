# Архитектура RUSEON Core

В этом документе описываются внутренние подсистемы ядра RUSEON. Он предназначен для Senior-инженеров и контрибьюторов, желающих понять, как система работает "под капотом".

## 1. Zero-Copy RingBuffer и Конвейер доставки (Delivery Pipeline)

В основе RUSEON Core лежит высокооптимизированный, дружелюбный к Garbage Collector пул памяти на базе `sync.Pool`. Когда видеокадр поступает по RTSP, он помещается напрямую в разделяемый кольцевой буфер (RingBuffer).

### Мультиплексирование (HLS & WebRTC)
И HLS Muxer, и WebRTC Muxer подписываются на один и тот же Zero-Copy RingBuffer.
* **HLS Muxer**: Группирует кадры в HLS-сегменты (Go/fMP4) и кэширует их в оперативной памяти. Когда клиент запрашивает `.m3u8` или `.ts`/`.m4s` сегмент, он отдается напрямую из памяти, что является фундаментальной защитой от проблемы "Thundering Herd" (Шторм подключений).
* **WebRTC Muxer (WHEP)**: Использует библиотеку `pion/webrtc` для мгновенной отправки NAL-юнитов (H.264/H.265) в активные PeerConnections. Так как WebRTC читает тот же самый RingBuffer, что и HLS, форкинг (разветвление) потока для Ultra-Low Latency доставки не потребляет дополнительных ресурсов CPU.

## 2. Инъекция ИИ-Метаданных (Zero-Transcoding Metadata)

Классическая обработка компьютерного зрения (например, YOLO Bounding Boxes или распознавание номеров) обычно требует полного ре-энкодинга видео для "выжигания" квадратиков на кадрах, что полностью уничтожает ресурсы CPU сервера.

RUSEON Core решает эту проблему путем маршрутизации метаданных Out-of-Band (вне основного медиа-канала):
1. **gRPC API**: Внешние ИИ-модули (например, `ruseon-yolo`) отправляют координаты детекций `[x, y, w, h]` и классы объектов в gRPC API ядра RUSEON.
2. **Metadata Broadcaster**: Ядро синхронизирует эти метаданные с текущими метками времени видео (PTS/DTS).
3. **WebRTC DataChannels**: Для клиентов WebRTC метаданные мгновенно пробрасываются через WebRTC DataChannel параллельно с видео-треком.
4. **HLS WebVTT**: Для HLS-зрителей метаданные на лету упаковываются в файлы субтитров `.vtt` (WebVTT). HLS Muxer внедряет теги `EXT-X-DATERANGE`, чтобы плеер мог синхронизировать таймлайн VTT с фрагментами видео.
5. **Client-Side Rendering (Frontend)**: React-клиент (`MetadataOverlay.tsx`) получает сырые координаты, масштабирует их относительно реальных размеров элемента `<video>` и рисует квадратики поверх видео с помощью HTML5 `<canvas>`. **На сервере при этом тратится 0% CPU на графику.**

## 3. Умный I/O Архиватор (`pkg/storage/localfs`)

Непрерывная запись гигабайтов fMP4 видеоданных 24/7 представляет серьезную угрозу для Linux-серверов: она стремительно забивает кэш операционной системы (OS Page Cache) грязными страницами (dirty pages). Это приводит к массивным `I/O stalls` (зависаниям дисковой подсистемы) и может спровоцировать принудительное убийство процессов через OOM Killer.

Для решения этой проблемы RUSEON Core использует технику сброса кэша **"Sliding Window" (Скользящее окно)**, встроенную напрямую в файловую абстракцию с использованием специфичных системных вызовов ядра Linux:

* **`sync_file_range`**: Вместо тяжеловесного `fsync()` (который блокирует тред и насилует журнал файловой системы обновлениями метаданных), мы используем `sync_file_range` с флагом `SYNC_FILE_RANGE_WRITE`. Это заставляет ядро асинхронно сбрасывать на диск только блоки данных текущего чанка (например, каждые 2 Мегабайта).
* **`SYNC_FILE_RANGE_WAIT_BEFORE | WAIT_AFTER`**: Как только чанк выходит за пределы активного окна, мы синхронно дожидаемся физического завершения его записи на диск.
* **`FADV_DONTNEED`**: Сразу после того, как чанк оказался на блинах диска, вызывается `unix.Fadvise(..., FADV_DONTNEED)`. Это приказывает ядру Linux мгновенно выкинуть именно эти страницы из оперативной памяти.

**Результат**: Данные стекают на диск ровным непрерывным потоком. OS Page Cache полностью защищен от вымывания, журнал файловой системы не трогается до момента финального закрытия видеофайла, а само Go-приложение никогда не блокируется на тяжелых операциях ввода-вывода (I/O).

## 6. Управление состоянием (Live API & BadgerDB)

Исторически RUSEON настраивался через config.yaml. В Enterprise-версии добавлена концепция **State Manager**. 
Настройки самого демона (порты, брокеры, GC) остаются в config.yaml, но конфигурация всех камер и их состояние теперь персистентно хранится в **BadgerDB**. 
Это позволяет добавлять и удалять потоки "на лету" через REST API (описано через Swagger swaggo/swag), без перезагрузки процесса, что критически важно для High Availability.

## 7. CLI инструмент (ruseon-cli)

Для удобства DevOps-инженеров реализована отдельная точка входа cmd/ruseon-cli. 
Утилита построена на базе spf13/cobra и выступает тонким клиентом к локальному REST API демона RUSEON. 
Это разделяет ответственность: демон занимается тяжелой работой, а CLI обеспечивает удобный Developer Experience (DX) для управления стейтом.

## 8. MQTT Publisher (IoT Gateway)

Для интеграции с внешними системами (Home Assistant, Node-RED, промышленные шины) реализован асинхронный воркер internal/mqtt. 
Чтобы сетевые задержки при публикации в MQTT-брокер не замедляли основной gRPC-стрим от ИИ-модулей, метаданные передаются в MQTT-воркер через **MPSC Lock-Free RingBuffer**. 
Это гарантирует строгую изоляцию (Zero-blocking) видео-пайплайна от сетевых флуктуаций IoT-инфраструктуры.
