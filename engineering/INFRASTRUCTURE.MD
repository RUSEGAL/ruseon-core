# Архитектура и Инфраструктура REA Stream Engine

Этот документ описывает аппаратные и сетевые требования для развертывания сервера видеостриминга (RTSP -> HLS/MP4) без транскодирования, написанного на чистом Go.

## 1. Сайзинг (Аппаратные требования)

Поскольку транскодирование видео отсутствует (zero-transcoding), основная нагрузка ложится на сеть (Сетевая карта) и дисковую подсистему (СХД). CPU и RAM используются в основном для перепаковки байтов (Muxing/Demuxing NAL-юнитов) и работы планировщика Go.

Ниже приведены примерные расчеты для реальной конфигурации: **HD (720p), 8 FPS, H.264 VBR (Максимальный битрейт 512 kbps)**.

| Количество камер + зрителей | Сетевая полоса (Суммарно)* | Процессор (CPU) | Оперативная память (RAM) | Дисковая система (Storage) |
|-----------------------------|---------------------------|-----------------|--------------------------|----------------------------|
| **10 камер / 10 зрителей**  | ~10 Mbps                  | 1 - 2 ядра      | 256 MB - 512 MB          | Обычный HDD/SSD            |
| **100 камер / 100 зрителей**| ~100 Mbps                 | 2 - 4 ядра      | 1 - 2 GB                 | Обычный SATA SSD / HDD     |
| **200 камер / 100 зрителей**| ~1.2 Gbps (пик)           | 6 ядер (Ryzen)  | 1.5 GB                   | SATA SSD                   |
| **1000 камер / 1000 зрит.** | ~1 Gbps (в среднем)       | 4 - 8 ядер      | 4 - 8 GB                 | Серверный SATA/NVMe SSD    |
| **10000 камер / 10000 зр.** | ~10 Gbps                  | 16 - 32 ядра    | 32 - 64 GB               | NVMe RAID / NFS-ферма      |

### Детализация расчетов (На основе реальных бенчмарков k6 / pprof):
* **Сеть:** Благодаря паттернам Zero-Copy и Lazy HLS, отдача видео работает с нулевой конвертацией. Реальный стресс-тест отдачи на 100 одновременных зрителей HLS показал пропускную способность **156 MB/s (~1.2 Gbps)** с медианной задержкой ответа **6 мс** и **0%** ошибок.
* **CPU:** Процессор расходуется исключительно на I/O-системные вызовы (события сети/диска) и парсинг байтов RTP (`gortsplib`). На 6-ядерном процессоре архитектура не испытывает никаких проблем с троттлингом (I/O Bound).
* **RAM (Память):** При 200 камерах со включенной постоянной записью на диск, потребление ОЗУ составляет всего **~1.4 ГБ** (~7 МБ на камеру). Основной расход идет на буферизацию NAL-юнитов и упаковку их в fMP4 чанки. В состоянии ожидания или без записи потребление будет в разы ниже.
* **СХД (Диск):** 1000 камер с макс. битрейтом 512 kbps постоянно пишут видео. Скорость записи: ~64 МБ/сек (непрерывно 24/7). Обычный серверный HDD (или недорогой RAID) легко справляется со скоростью последовательной записи 64 МБ/сек, дорогие NVMe здесь не обязательны, если нет тысяч параллельных зрителей архива.

## 2. Хранение архива (Записи видео)

Для обеспечения максимальной производительности при большом количестве камер (например, 1000+) и возможности горизонтального масштабирования (подключение дополнительных серверов для раздачи HLS), рекомендуется использовать сетевую файловую систему **NFS (Network File System)** версии 4.x.

### Настройка NFS (Сетевое хранилище)

Сервер хранения (Storage Server) расшаривает директорию по NFS. Основной сервер (REA Stream Engine) монтирует её как локальную папку (по умолчанию `recordings/`). 

Поскольку сервер непрерывно пишет множество крупных файлов (`.mp4`), стандартные параметры монтирования ОС Linux могут быть неоптимальны и приведут к зависаниям (I/O Wait).

**Рекомендуемая команда для монтирования NFS-шары на основном сервере:**

```bash
mount -t nfs -o vers=4,tcp,rsize=1048576,wsize=1048576,noatime,async,soft,timeo=100,retrans=2 192.168.1.100:/path/to/archive /opt/gritprof/recordings
```

### Расшифровка параметров монтирования (для Linux):

* `vers=4` — использование NFS v4 (более быстрый и безопасный протокол).
* `tcp` — использование TCP для предотвращения потери пакетов при высоких нагрузках.
* `rsize=1048576`, `wsize=1048576` — увеличение размера пакета чтения/записи до 1 МБ (максимально допустимое в современных ядрах). Резко снижает нагрузку на CPU и увеличивает пропускную способность для больших медиа-файлов.
* `noatime` — отключение обновления времени последнего доступа к файлам при чтении. Избавляет сервер хранения от лишних мелких операций записи на диск при каждой выдаче HLS-сегмента архива зрителям.
* `async` — асинхронная запись (ОС не ждет подтверждения от жесткого диска для каждого байта).
* `soft,timeo=100,retrans=2` — если сервер хранения временно недоступен или моргнула сеть, процессы Go не уйдут в бесконечное (uninterruptible) зависание. Через 10 секунд (timeo=100 децисекунд) после 2 безуспешных попыток система выдаст I/O ошибку, и наше приложение сможет обработать её штатно (например, переподключить запись локально или пересоздать файл).

## 3. Масштабирование (Scale-Out)

При превышении порога в 1 000 - 2 000 потоков, удержание всего функционала на одном сервере становится рискованным из-за ограничений одной сетевой карты (10GbE) и Сборщика мусора Go (GC).

**Рекомендуемая архитектура для 10 000+ потоков:**
1. **Балансировщик нагрузки (L4 - HAProxy / Nginx):** Распределяет зрителей HLS между нодами раздачи.
2. **NFS Cluster / Ceph (СХД):** Отдельный отказоустойчивый кластер для записи `mp4`.
3. **Ingest-ноды (Захват видео):** Несколько независимых серверов Gritprof (по 1000-2000 камер на каждый), которые только стягивают RTSP с IP-камер и пишут их на примонтированный NFS диск.
4. **Egress-ноды (Раздача HLS):** Несколько серверов Gritprof, которые не обрабатывают RTSP, а только читают готовые `.mp4` куски из NFS по запросу от зрителей, на лету формируя HLS манифесты и отдавая трафик клиентам.

## GitHub Actions & CI/CD Pipelines

С развитием Enterprise-функционала инфраструктура пайплайнов была расширена:

- 	est.yml — Запускается на каждый Push и PR. Прогоняет быстрые Unit-тесты и Fuzz-тесты. Гарантирует базовую целостность ядра перед ревью кода.
- performance.yml — Нагрузочное тестирование (k6). Запускается на PR для защиты ядра от регрессий пропускной способности. Собирает бинарник, стартует сервер и эмулирует нагрузку, проверяя SLA (latency < 200ms, errors < 1%).
- 
ightly.yml — Тяжелые E2E-тесты на базе 	estcontainers-go. Поднимает Docker-инфраструктуру (Mediamtx + FFmpeg) для эмуляции RTSP-потока и проверки полного пайплайна (Ingest -> WebRTC/HLS). Запускается каждую ночь (02:00 UTC), чтобы не тормозить дневной CI.
