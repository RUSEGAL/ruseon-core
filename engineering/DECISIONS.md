# Журнал решений (Decisions)

Этот файл содержит архитектурные и технические решения, принятые в процессе разработки.

## 1. Zero-Transcoding
**Проблема**: Декодирование и кодирование видео (H.264/H.265) для 1000+ камер требует колоссальных ресурсов CPU/GPU.
**Решение**: Сервер работает в режиме "перепаковки" (Muxing). Он извлекает сырые NALU (Network Abstraction Layer Units) из RTP пакетов (через RTSP) и на лету упаковывает их в HLS (MPEG-TS) и fMP4 без транскодирования. Это позволяет одному серверу обрабатывать тысячи потоков.

## 2. Ring Buffer (Кольцевой буфер)
Для обеспечения работы без копирования (zero-copy) и моментального старта трансляции для новых зрителей, каждый видеопоток пишет данные в кольцевой буфер в оперативной памяти. Буфер хранит последние несколько секунд видео (начиная с I-frame) и позволяет раздавать HLS-сегменты без обращений к жесткому диску (Disk I/O).

## 3. Запись архива (fMP4 Recorder)
**Проблема**: Запись "классического" MP4 файла требует обновления заголовков в начале файла после завершения записи. При сбое питания файл становится битым (unplayable).
**Решение**: Использование фрагментированного MP4 (fMP4). Видео записывается небольшими независимыми фрагментами (moof+mdat атомы). Даже если запись прерывается внезапно, файл остается валидным и его можно воспроизвести в VLC или браузере вплоть до последней секунды перед сбоем.

## 4. СУБД: BadgerDB
Изначально данные хранились в `config.yaml`, но с появлением динамического биллинга, большого количества камер и тегов, начались проблемы с гонками данных и производительностью (I/O).
**Решение**: Переход на встраиваемую NoSQL Key-Value базу данных **BadgerDB**. Она написана на чистом Go, использует LSM-деревья, работает с огромной скоростью (как в RAM, так и на диске) и обеспечивает атомарность транзакций (ACID) без необходимости разворачивать сторонние БД вроде PostgreSQL или Redis.

## 5. Timeshift и Умный экспорт архива
Для просмотра архива через Web UI было решено не генерировать HLS-сегменты на диске (что съело бы в 2 раза больше места), а конвертировать сохраненные `fMP4` файлы в HLS `.ts` сегменты "на лету" прямо в оперативной памяти при запросе.
Экспорт нужного диапазона архива работает нативно: сервер парсит коробки (boxes) MP4-файла и сшивает их байт-в-байт без перекодирования.

## 6. Биллинг (Трекинг трафика)
Трафик считается на основе принятых от камеры байтов (на уровне RTP парсера), так как это наиболее точный показатель "полезной" работы сервера.

## 7. Фронтенд (React)
Для Web UI выбран стек React + Vite + TypeScript. Дизайн основан на принципах Glassmorphism (эффект матового стекла), чтобы придать интерфейсу современный, "дорогой" и технологичный вид.

## 8. Бэкапы БД (Гибридная модель)
Для надежности используются два механизма:
1. Автоматический: Фоновый воркер делает нативный бинарный снапшот БД на диск каждые 24 часа.
2. Ручной: Эндпоинты экспорта и импорта данных в JSON для удобного переноса конфигураций администратором через Web UI.

## 9. Ленивый HLS (Lazy Muxing)
**Проблема**: Постоянная генерация HLS (MPEG-TS) сегментов для всех камер расходует ресурсы CPU и памяти (на аллокации буферов), даже если поток никто не смотрит.
**Решение**: HLS Muxer переводится в режим "по требованию" (On-Demand). Этот режим является **настройкой для каждой конкретной камеры** (включается опционально).
- Muxer создается только при запросе плейлиста или сегмента (через вызов `WakeUpHLSMuxer()`).
- Внутри объекта `Stream` работает фоновый `watchdog`. Если к HLS нет обращений более 15 секунд, Muxer уничтожается.
- При пересоздании Muxer мгновенно считывает исторические кадры (последние 4 секунды) из `RingBuffer` и генерирует стартовые сегменты без задержек для клиента.
- Запись архива (`fMP4 Recorder`) остается независимым читателем `RingBuffer` и продолжает писать данные на диск без перебоев.
