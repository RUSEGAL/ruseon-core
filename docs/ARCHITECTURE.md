# Архитектура GritprofMediaServer

## 1. Общее описание
GritprofMediaServer - это высокопроизводительный сервер, принимающий видеопотоки RTSP от IP-камер и раздающий их по протоколу HLS, а также сохраняющий архив в формат fMP4.
Основной упор сделан на работу без транскодирования (zero-copy/muxing), отсутствие лишних зависимостей и максимальную производительность.

## 2. Поток данных (Data Flow)

1. **Инициализация:** При старте сервер загружает статику из `config.yaml` (порт, логи) и динамические данные из СУБД `BadgerDB` (камеры, теги).
2. **Захват потока:** Для каждой активной камеры создается объект `Stream`. Запускается `RTSPClient` (на базе `gortsplib`), который подключается к камере.
3. **Парсинг:** RTP-пакеты от камеры парсятся в сырые NAL-юниты (H.264/H.265). На этом же этапе `Billing` считает входящие байты и списывает их с квоты камеры.
4. **Буферизация:** NAL-юниты записываются в `RingBuffer`. Буфер хранит последние кадры (включая I-frames) в оперативной памяти, чтобы новые зрители могли сразу получить готовую картинку без задержек и Disk I/O.
5. **Раздача (Live HLS):** При запросе от зрителя, HLS Muxer читает NAL-юниты из `RingBuffer` и упаковывает их в TS-сегменты на лету.
6. **Архивация:** Параллельно `Recorder` читает те же NAL-юниты из `RingBuffer` и записывает их на жесткий диск в формате фрагментированного MP4 (fMP4), разбивая файлы по часам.

## 3. Подсистема Архива (Timeshift & Export)
Архив пишется на диск в файлы вида `recordings/camera-id/2026-07-31_15-00-00.mp4`.
1. **Просмотр архива (Timeshift):** При запросе из Web UI, парсер `go-mp4` читает нужный `.mp4` файл, извлекает из него NAL-юниты и прямо в оперативной памяти упаковывает их в HLS `.ts` сегменты. Таким образом, серверу не нужно хранить двойной объем данных (и HLS, и MP4).
2. **Экспорт (Склейка):** При скачивании фрагмента видео, сервер считывает `moov`/`mdat` коробки нужных файлов, склеивает их байт-в-байт и отдает готовый обрезанный MP4 файл без участия процессора.

## 4. СУБД (Storage Layer)
Все изменяемые данные (камеры, их настройки, пользовательские теги, лимиты трафика, история отключений) хранятся в Key-Value базе **BadgerDB** (папка `data/`). 
Это позволяет использовать атомарные транзакции и не бояться потери или порчи данных при одновременном редактировании через UI.

## 5. Структура проекта (Go Project Layout)
```text
.
├── cmd/
│   └── server/
│       └── main.go           # Точка входа в приложение
├── internal/
│   ├── api/                  # HTTP-обработчики (Gin), роуты, трекер клиентов
│   ├── archive/              # Работа с записанными MP4 (Индексатор, Timeshift HLS, Экспорт)
│   ├── backup/               # Фоновый воркер для бэкапов БД
│   ├── buffer/               # Кольцевой буфер и работа с кадрами
│   ├── config/               # Статические настройки сервера (config.yaml)
│   ├── logger/               # Настройка zerolog
│   ├── recorder/             # Запись Live-потока в fMP4, ротация файлов
│   ├── rtsp/                 # Подключение к камерам (gortsplib)
│   ├── storage/              # Слой работы с BadgerDB (CRUD для камер и тегов)
│   └── stream/               # Менеджер потоков, Биллинг трафика, Стриминг HLS
├── web/                      # Исходники Frontend (React + TypeScript + Vite)
├── docs/                     # Архитектурная документация (MD)
├── data/                     # (Генерируется) База данных BadgerDB
├── recordings/               # (Генерируется) Видеоархив MP4
└── config.yaml               # Главный конфигурационный файл
```
